**为什么这条证据是有效的**：首帧在全程的 **0.1%** 处到达（29ms / 30070ms）。如果 SSE 只是在收工时把缓冲一次性倒出来，首帧会在 30s 附近才出现 —— 这正是这条断言要排除的情况。另外用浏览器验过同一件事的界面侧：US-304 走查里实时块从 +0.23s 一直存活到 +2.87s，`已用时` 连续走秒 `00:00 → 00:01 → 00:02`（见 `US-304-前端实时进度.md`）。

**保留的小事实**：S1 现在的轨迹颗粒度是「1 `thought` → 1 `llm.call` → 1 `decision`」，所以 30 秒里界面上只有 1 步、走秒在动。更细的分段要等 Sprint 4 内核的工具调用循环（一次任务落几十次 `step`）。这是 **S1 的产出形态**，不是订阅层的问题。

关键的一行是 `test_approve_issues_grant_and_resumes_without_manual_budget_edit`（`tests/test_budget_grants.py:136`）：它走的**已经是异步路径** ——（下面是为了看清链路而压缩的片段，真实断言见源码）

```python
resp = client.post(f"/api/projects/{project_id}/stages/S1/run")          # :130 返回 job_id，不是同步结果
assert resp.status_code == 202                                          # :131 受理即返回

approved = client.post(f"/api/approvals/{pending[0]['id']}/approve", json={}).json()
```

即：受理 → `job_id` → 轮询作业台账 → 熔断变 `paused` → 批准签发豁免 → 再跑变 `succeeded`，中间**没有任何手工改额度的动作**（源码里那句注释写得很直白：`# 关键：这里**不再**手工改回 budget_steps`）。同步路径上的旧验证已由这一组取代。

顺带覆盖的边界：豁免的额度是真约束（`test_grant_amount_is_a_real_constraint`）、批准可显式指定额度、批准留审计决策、批准后重启失败不丢批准（`test_approval_survives_a_failed_resume`）、拒绝不签发豁免。

## 迁移安全 — ✅ 通过

Sprint 3 一口气加了 5 张表（`budget_grants` / `app_config` / `llm_cache` / `jobs` / `job_events`）。加表迁移最常见的翻车方式是顺手把老表重建一遍，数据没了而不自知。三条证据：

1. **自动化测试**（`tests/test_migrations.py`）：
   - `test_upgrade_adds_new_tables_without_touching_existing_rows`（:53）—— 从 `9f3c1a7b5d20` 起一份带真实数据的库，升级到 head，断言 4 张新表出现 **且老表逐表行数一字不差**、老项目记录仍读得回来；
   - `test_upgrade_to_head_is_idempotent`（:77）—— 启动路径会无条件调一次 `upgrade head`，第二次必须是 no-op（表集合与行数都不变）。
2. **全新库冷启动**（本次 G1-2 留证顺带）：日志显示 5 个迁移从空库顺序跑到 `7c1f9a34e5d2 (head)`，无报错。
3. **真实库副本**（`shutil.copy2` 绝对路径法，真实库全程未动）：意外地成了最有力的一条 —— 本机真实库还停在 `246a42e41036`（**Sprint 2 末**，根本没进过 Sprint 3），副本上连升 3 个迁移到 head：
